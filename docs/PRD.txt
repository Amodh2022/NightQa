Android apps follow in a later phase. Who it's for: small software teams (2 to 20 engineers) in India with no dedicated QA person, starting with startups and development agencies. Value in one line: wake up to proven bugs with ready-to-review fixes, not a list of maybes. How it's different: it tests the way Indian users actually use apps (small Android screens, slow networks, OTP logins, UPI payments, Indian languages), and it closes the loop from bug to fix. Status: idea stage. A two-week test with 5 real teams decides whether to build the full product (see Release plan). Problem Small teams now ship code faster with AI help, but nobody tests it like a real user before customers do. A typical story. A 6-person startup ships a checkout change on Friday. On Saturday, users on slow mobile data can't finish a UPI payment. The team finds out on Monday from angry support messages. What makes this worse: AI-written code is often almost right. In Stack Overflow's 2025 survey of 49,009 developers, 66% said AI solutions are almost right but not quite, and 45% said debugging AI code takes more time ( The Register ). Incidents are rising. Momentic, a competitor, cites a Faros AI report that monthly incidents rose nearly 58% as AI adoption accelerated ( Momentic ). This is a vendor citing a vendor, so treat it as directional. Small teams have no QA person. Developers click through the happy path before a release and hope. This is a hypothesis to confirm in interviews. Indian conditions go untested. Apps are built on fast laptops and Wi-Fi but used on budget Android phones, patchy networks, OTP logins and UPI payments. Also a hypothesis to confirm. A bug report is not a fix. Vague reports take hours to reproduce, and a confirmed bug still needs a developer to find the cause and change the code. It is the main way a team tells NightQA what \"correct\" means. User story. As a tester, I write the checkout journey once in plain words, so it is checked every night without me clicking through it. Example flow Parts of a flow Field Meaning Required flow Short name shown in reports Yes start Page where the flow begins Yes login Name of a saved test account No steps Actions in order, in plain words Yes expect What must be true after a step At least one per flow variations Risky versions of the flow to try No tags Labels like \"payments\" or \"critical\" for filtering and priority No Three ways to create flows Write YAML files in a nightqa/ folder in the repo, reviewed like code. Fill a simple form in the dashboard (V1). Import test cases from Excel or CSV: one row becomes one flow, and the user confirms each before saving (V1). Rules that keep flows reliable Every expectation must be checkable. \"Total becomes \u20b9449\" works; \"page looks fine\" gets a warning asking for something specific. Passwords, OTP codes and payment details never live in flow files. Flows refer to saved test accounts by name. A flow that fails on its first run for setup reasons (bad login, missing test product) is marked \"needs setup\", not reported as a bug. Acceptance criteria A malformed flow file shows a clear error naming the line and the problem. A vague expectation shows a warning with an example of a better one. An imported Excel row becomes a draft flow the user can edit before saving. Feature: Flow runner and verdicts The runner performs each flow in a real browser, checks every expectation, and ends with one clear verdict. After the first successful run, nightly checks become cheap replays and AI is used only when something changes. How one run works Prepare. Open a fresh browser, apply the chosen network and screen profile, and log in with the saved test account. Look. The agent takes a screenshot and a list of the buttons, links and fields on the page. Act. It picks the next action (click, type, scroll, wait, go to a page) to complete the current step, and does it. Check. After a step with an expect , it checks the page text, element states and screenshot, then records pass or fail with evidence. Stop safely. Each flow has a step and time budget, so a confused agent can't loop forever or burn money. Verdicts Verdict Meaning What happens next Pass Every expectation met First pass is saved as a regression test Bug An expectation failed, or the app showed an error Sent to the reproducer App changed The flow broke because the app changed on purpose, such as a renamed button Updated test proposed; team confirms Needs setup The flow couldn't start: login failed, test data missing, staging down Team notified; not counted as a bug Agent stuck The agent couldn't work out how to do a step Flow author asked to reword that step Bugs caught even without an expectation: uncaught JavaScript errors, server errors (5xx), blank pages, spinners that never finish, and in-app links that lead to \"page not found\". Regression replay and self-healing The first passing run is saved as a Playwright test: the exact actions and the elements used. Later nights replay that test directly. It is fast, cheap and repeatable. If a replay fails, it retries once to rule out a random glitch. If it still fails, AI compares the page with the last good run and decides between Bug and App changed. App changed never edits the saved test silently. The team approves the update, so a real bug can't be \"healed\" away. Acceptance criteria Every verdict links to its video, screenshots and logs. A run that hits its budget ends as Agent stuck, never as Pass. A replay that passes uses no AI calls. Feature: Exploration and the reproducer Exploration finds bugs that no flow covers, and the reproducer makes sure only repeatable bugs ever reach the team. The reproducer is the most important quality feature in the product. Exploration with personas The agent wanders the app as different kinds of users, starting from each flow and branching off it. Persona What it tries Impatient user Double-clicks, skips optional fields, presses back in the middle of actions Careless typer Empty fields, very long text, emojis, special characters, letters in a phone field Slow network user 3G speed, reloads while pages load, waits through timeouts Budget phone user Small screens; checks buttons are visible and reachable Regional-language user Hindi or Kannada text in forms and search (deeper support in V2) Safety and scope controls Allowed and blocked pages: the team blocks risky actions like \"delete account\" or \"email all users\". Limits: maximum sessions per night and steps per session, so cost stays predictable. Coverage memory: the agent remembers pages already visited and spends later nights on new areas. How the reproducer works Take the exact list of actions that led to the suspected bug. Replay it three times in fresh browsers with the same profile. Classify it: Confirmed (happens every time), Flaky (happens sometimes) or Not reproduced (discarded). Shorten it: remove steps that aren't needed, so the bug has the shortest possible recipe. Rate severity, then report only confirmed bugs at or above the team's chosen level. Severity Example Critical Login or payment can't be completed High A feature is broken but the app still works Medium An error shows, but there is a workaround Low A console error with no visible effect Flaky bugs go to a separate \"needs a look\" list instead of GitHub. Acceptance criteria No bug reaches GitHub unless it reproduced on every replay. Blocked pages are never visited, including through links. Each confirmed bug has a recipe of the fewest steps that still triggers it. Feature: Failing tests, GitHub issues and fix PRs Every confirmed bug becomes a failing test and a GitHub issue, then a coding agent proposes a fix that CI and a human must approve. NightQA never merges anything. Failing test writer Turns the bug's shortest recipe into a Playwright test, saved where the repo keeps tests, for example tests/nightqa/checkout-coupon.spec.ts . Runs the test against staging. It must fail, and fail for the bug's reason. A test that passes is thrown away. Uses stable ways to find elements (labels, roles, test ids) instead of fragile page positions. Before opening an issue, NightQA checks its open issues for the same page, error and failed expectation. A repeat adds a \"seen again\" comment instead of a new issue. Fix pull requests In the MVP, the issue triggers the team's own coding agent. For example, Claude Code GitHub Actions responds to an @claude mention in an issue and can create a pull request ( docs ). The team installs it and lists NightQA's bot in the action's allowed_bots setting, because the action ignores bot accounts by default. NightQA itself needs no write access to code. The PR must include the failing test plus the code change, and CI must run that test. Limits: at most 3 fix PRs a night by default, only for High or Critical bugs. Teams can switch to manual: comment on the issue to request a fix. Review, merge and learning A developer always reviews and merges. Nothing is auto-merged. NightQA tracks each PR (open, merged, closed) to measure the merged fix rate. When a PR is closed, a one-click reason (\"wrong fix\", \"not a bug\", \"won't fix\") helps NightQA improve its reports. Merged tests stay in the repo as regression tests, and NightQA replays them every night. GitHub permissions requested: read and write issues, read pull requests, read repository metadata. Read access to code is optional, used only to match the repo's test folder conventions. Acceptance criteria Every issue includes a failing test that was run and failed. A repeated bug never creates a second issue. No more fix PRs are triggered in a night than the team's limit. Setup, security and safety A team should get its first report within 30 minutes of setup, and NightQA must never touch production, real money or real customers. Setup in six steps Sign up with GitHub. Add the app: a staging URL (web) or a staging APK (Android, V2). Add test accounts and, if needed, a test OTP. These are stored encrypted. Install the NightQA GitHub App on the repo. For fix PRs, also install a coding agent and allow NightQA's bot to trigger it. Write or import the first flow, or accept flows NightQA suggests after a quick look around the app. Click \"Run now\", read the first report, then set the nightly schedule. Security and privacy Staging only. URLs that look like production need an explicit confirmation, and production testing is off by default. Secrets. Test passwords and OTPs are encrypted at rest, never written to logs, and hidden in screenshots where possible. Stored evidence. Videos, screenshots and logs are kept 30 days by default, and teams can delete them anytime. Data location. The hosted version runs in an Indian cloud region. AI processing. Screenshots and page text are sent to the AI provider to decide actions. This is disclosed during setup. Personal data. Staging should hold test data, not real customer records. If it does hold personal data, India's DPDP Act may apply; get legal advice before launch. Least privilege. GitHub access is limited to issues, PR status and metadata. Team roles. Owner, member and viewer, plus an activity log of runs and changes. Agent safety rules Never visit blocked pages or perform blocked actions. Never send messages to real people, or pay with real money. Limit request speed, and stop a run if staging starts returning many errors, so NightQA never overloads a team's server. Acceptance criteria A new team reaches its first report in under 30 minutes of setup time. No secret appears in any log, report or GitHub issue. Deleting a project removes all its stored evidence within 24 hours. Technical architecture One TypeScript codebase runs everything: a queue hands nightly jobs to agent workers, which drive the staging app, ask Claude what to do next, and report through GitHub and Slack. The worker is the heart of the product; everything else stores, schedules or reports its results. Fixes are made by the team's own coding agent inside their repo, never by NightQA directly.
